## What is MCP?

The **Model Context Protocol (MCP)** is an open standard for connecting AI applications to external tools and data sources — think of it as a standardized port that lets any compatible client (Cursor, Claude Code, Codex, etc.) talk to any compatible server without custom integration code per pair.

Shanone *is* an MCP server: connect once, and any MCP client gets programmatic access to Shanone's integration catalog, Skill library, and (for admins) permission-management tools.

## Why a meta-tool pattern, not one tool per action

Shanone's backend implements 269+ service integrations, each with dozens to hundreds of individual actions (Stripe alone has 328). Registering every single action as its own MCP tool would flood your agent's context window before it even started working. Instead, Shanone follows a **Tool Vendor** pattern — similar to how Composio structures its catalog — exposing a small, fixed set of meta-tools that search, inspect, and execute against the full catalog on demand:

A parallel **Skill Vendor** pattern does the same for reusable, saved workflows (`shanone_list_skills` → `shanone_get_skill`), and a **Permission Vendor** set of tools lets Root/delegated administrators control who can use what.

## Server architecture

Shanone actually ships two things that both speak MCP, sharing the exact same tool set:

| Component | Transport | What it is |
|-----------|-----------|-----------|
| **Remote MCP server** | Streamable HTTP at `/mcp` | Runs inside Shanone's backend process itself. Calls `src.services.tool_vendor` directly — no extra network hop. This is what the `X-Org-Id`-gated direct connection in [Setup](/mcp/setup) talks to. |
| **Local stdio proxy** (`@duzzle/shanone-mcp` npm package, or the Python `apps/mcp-server` package) | stdio | Runs on your machine, forwards each MCP tool call to Shanone's REST API (`/api/v1/tools/...`, `/api/v1/skills/...`, `/api/v1/permissions/...`) over HTTPS using your API key. This is the easiest path for clients that don't support custom HTTP headers. |

Both expose the same meta-tools with the same names and parameters — pick whichever transport your client supports better. See [Setup](/mcp/setup) for exact configuration.

## Authentication

Every request — whether through the direct HTTP endpoint or the local proxy — is authenticated with your Shanone API key:

```
Authorization: Bearer sh_xxxxxxxxxxxxxxxx
```

(`X-API-Key: sh_xxx` also works.) The **direct remote endpoint** additionally requires your organization ID as a second, composite factor — sent as an `X-Org-Id` header or `?org_id=` query parameter — so a leaked API key alone can't be used to call your tools. The local stdio proxy doesn't need this second factor; it only requires the API key. See [Authentication](/api-reference/authentication) for the full picture, including rate limits.
