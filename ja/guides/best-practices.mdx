## タスク志向で、ツール志向にならない

`shanone_search_tools`は*タスク*の説明との関連度でランキングされる仕組みであり、ツール名による検索ではありません。タスクを具体的に表現したクエリは、少数の使いやすい結果を返します。一方、大規模なインテグレーション(Slackは139個、Stripeは328個のツールを持つ)に対して単にサービス名だけを渡すと、結果が多すぎたり、的外れなものが返ってきたりします。

<Tabs>
  <Tab title="良い例">
    "Post a message to a Slack channel"

    "Create a GitHub issue with a title and body"

    "Get the ETH balance of an address"
  </Tab>
  <Tab title="悪い例">
    "Slack"

    "github"

    "do something with ethereum"
  </Tab>
</Tabs>

## 「すべて」が欲しいときは全件リストを依頼する

あなた(またはエージェント)が本当に欲しいのが、そのサービスの最も関連性の高い数件ではなく完全なツール一覧である場合は、それを明示的に伝え、`shanone_search_tools`ではなく`shanone_list_service_tools`をエージェントに呼び出させてください。これは特に大規模なインテグレーションで重要です。

| サービス | ツール数 |
|---------|-----------|
| Stripe | 328 |
| HubSpot | 214 |
| GitHub | 176 |
| Slack | 139 |
| Ethereum | 76 |
| Google Calendar | 58 |
| Gmail | 52 |
| Jira | 55 |
| Linear | 46 |
| Notion | 45 |

`shanone_search_tools`は、このくらいの規模のサービスであってもすべてのツールを表示することを保証するものではありません——レスポンス内の`has_more`を確認し、`true`であればクエリを絞り込むか、`shanone_list_service_tools`に切り替えてください。

## スキーマ確認のステップを働かせる

不慣れなツールについては、`shanone_execute_tool`の前にエージェントに`shanone_get_tool_schema`を呼び出させてください。これにより、引数名の当てずっぽう(Shanoneのツールはわかりやすいものの、必ずしも直感的とは限らないフィールド名を使います——例えば`slack_post_message`は`channel_id`ではなく`channel`を取ります)を避け、必須項目と任意項目を事前に把握できます。

<Steps>
  <Step title="検索する">
    タスクを表現したクエリで`shanone_search_tools`を呼び出す。
  </Step>
  <Step title="確認する(不安なとき)">
    検索結果から得た正確なツール名で`shanone_get_tool_schema`を呼び出す。
  </Step>
  <Step title="実行する">
    スキーマに合わせた引数のJSON文字列で`shanone_execute_tool`を呼び出す。
  </Step>
</Steps>

## ワークフローはSkillとして保存し、繰り返さない

同じ複数ステップの指示をエージェントに何度も伝えていることに気づいたら(例:「Notionのプロジェクトページを確認し、要約してSlackに投稿する」)、`shanone_create_skill`で保存しましょう。Skillはサーバー側に保存されるため、同じワークフローがShanoneアカウントに接続するどのマシン、どのIDE、どのエージェントからでも利用できます——さらにShanoneのWebダッシュボードにも表示されます。

<CardGroup cols={2}>
  <Card title="まず確認する" icon="magnifying-glass">
    複雑な複数ステップのタスクに取り掛かる前に`shanone_list_skills`を呼び出す——チームの誰かが既に保存しているかもしれません
  </Card>
  <Card title="わかりやすい名前を付ける" icon="tag">
    Skillの`name`と`summary`だけが一覧結果に表示されます——後で見て分かるくらい具体的な名前にしましょう
  </Card>
</CardGroup>

## 認証の壁はうまくいなす

`shanone_execute_tool`が`reason: "auth_required"`または`"auth_expired"`を返したとき、それは回避すべき失敗ではありません——Shanoneが「そのサービスはまだ接続されていない」と伝えているだけです。ユーザーに`connect_link`を提示し、OAuthの完了を待ってから、*まったく同じ*ツール呼び出しを再試行してください。

<Note>
`auth_required`に遭遇したときに、エージェントに別のツールや回避策を試させないでください。対処法は常に同じです。接続リンクにアクセスしてから再試行する、それだけです。
</Note>

## 権限は最小権限を保つ

RootユーザーまたはSA2の委任管理者である場合、デフォルトで全メンバーに全サービスを有効化することは避けましょう。あるロールに不要なサービス(例: エンジニアへの請求ツール、営業担当へのインフラツール)は`shanone_set_user_service_permission`で無効化し、新しい社員のオンボーディング時に権限セット全体を一括で設定する場合は`shanone_batch_set_user_permissions`を使ってください。詳しいモデルは[権限とアクセス制御](/ja/product-guide/permissions)を参照してください。

## よくある落とし穴

| 落とし穴 | 対処法 |
|---------|-----|
| 大規模なインテグレーションに対して単語1つのサービス名で検索する | 全件を列挙するには`shanone_list_service_tools`を使うか、クエリにタスクの詳細を加える |
| 不慣れなツールの引数名を当てずっぽうで指定する | まず`shanone_get_tool_schema`を呼び出す |
| 同じ複数ステップのワークフローをセッションごとに説明し直す | 一度Skillとして保存する |
| `auth_required`エラーの後、別のツールで失敗した呼び出しを再試行する | `connect_link`をたどってから、同じ呼び出しを再試行する |
| 「念のため」に全サービスを全メンバーへ許可する | ロールごとに権限を絞る。後から締め直すよりも最初から絞る方が簡単 |
